## Background: The Batch-Scoring DAG

The DAG models a realistic batch-scoring pipeline with this structure:

```txt
        extract
           │
           ▼
        score
       /    \
      ▼      ▼
    load   notify
```

- **extract**: List every `*.jpg` under `data/fixtures/` (both camera profiles)
- **score**: Run the detector over each image, accumulate detection counts
- **load**: Write `batch_report.json` — depends only on `score`
- **notify**: Deliberately **flaky** task (fails twice, then succeeds) simulating a webhook/Slack notification — also depends only on `score`. Exercises retry logic in a real DAG run.

### Function 1: `topological_order(tasks)` — Kahn's Algorithm

**Purpose**: Order tasks so every task runs after its dependencies. Detect cycles and missing dependencies.

#### Algorithm: Kahn's Topological Sort

```python
def topological_order(tasks: Dict[str, Task]) -> List[str]:
    """
    Given a dict of {task_name: Task}, return a list of task names such
    that every task appears AFTER all the tasks in its `depends_on`.

    If there's more than one valid order (e.g. two independent tasks that
    both depend on the same upstream task), any valid order is fine.

    If the tasks contain a dependency cycle (or a task depends on a name
    that doesn't exist in `tasks`), raise ValueError.

    Hint: Kahn's algorithm — compute in-degree (number of dependencies) for
    every task, repeatedly pick a task with in-degree 0, "remove" it
    (decrementing the in-degree of everything that depended on it), and
    append it to the result. If you run out of in-degree-0 tasks before
    placing every task, there's a cycle.
    """
```

#### Implementation Logic

```python
# Step 1: Build graph structure
in_degree = {name: 0 for name in tasks}    # Track how many deps each task has
adj = {name: [] for name in tasks}          # Adjacency list: who depends on whom

# Step 2: Validate dependencies and populate graph
for name, task in tasks.items():
    for dep in task.depends_on:
        if dep not in tasks:
            raise ValueError(f"Task '{name}' depends on missing task '{dep}'")
        adj[dep].append(name)               # dep → name (dep must run before name)
        in_degree[name] += 1                # Increment in-degree of dependent

# Step 3: Kahn's algorithm - find nodes with in-degree 0
queue = [name for name, deg in in_degree.items() if deg == 0]
result = []

while queue:
    current = queue.pop(0)                  # Any in-degree-0 node works
    result.append(current)

    # "Remove" current: decrement in-degree of its dependents
    for neighbor in adj[current]:
        in_degree[neighbor] -= 1
        if in_degree[neighbor] == 0:
            queue.append(neighbor)

# Step 4: Cycle detection
if len(result) != len(tasks):
    raise ValueError("Dependency cycle detected in tasks")

return result
```

#### Key Design Decisions

| Aspect | Implementation |
|--------|----------------|
| **Graph representation** | Adjacency list + in-degree map (O(V+E) space) |
| **Missing dependency check** | Early validation during graph construction |
| **Cycle detection** | If result length ≠ total tasks → cycle exists |
| **Tie-breaking** | FIFO queue (`pop(0)`) — deterministic but any valid order accepted |
| **Error messages** | Descriptive: mentions specific task and missing dependency |

#### Test Cases Covered

1. **Linear chain**: `a → b → c` → order `[a, b, c]`
2. **Branching DAG**: `extract → score → {load, notify}` → score before both
3. **Cycle detection**: `a ↔ b` → `ValueError`
4. **Missing dependency**: `a depends on "does_not_exist"` → `ValueError`

### Function 2: `run_task_with_retry(task, context)` — Retry Logic

**Purpose**: Execute a task with retry semantics matching Airflow's `retries` parameter.

#### Specification

- Run `task.fn(context)`
- If it raises, retry up to `task.max_retries` **additional** times
  - `max_retries=2` → up to 3 total attempts
- Sleep `task.retry_delay_seconds` between attempts
- On success: return number of attempts (1 = first try)
- On total failure: propagate the **last** exception (don't swallow)

#### Implementation Logic

```python
def run_task_with_retry(task: Task, context: dict) -> int:
    """
    Run `task.fn(context)`. If it raises, retry up to `task.max_retries`
    additional times (so max_retries=2 means up to 3 total attempts),
    sleeping `task.retry_delay_seconds` between attempts (use time.sleep).

    If the task eventually succeeds, return the number of attempts it took
    (1 if it succeeded on the first try).

    If it never succeeds, let the LAST exception propagate (don't swallow
    it) after all retries are exhausted.
    """
    last_exception = None
    max_attempts = task.max_retries + 1

    for attempt in range(1, max_attempts + 1):
        try:
            task.fn(context)
            return attempt                    # Success! Return attempt count
        except Exception as e:
            last_exception = e                # Remember the exception
            if attempt < max_attempts:
                time.sleep(task.retry_delay_seconds)

    # All retries exhausted — propagate the last exception
    raise last_exception
```

#### Key Design Decisions

| Aspect | Implementation |
|--------|----------------|
| **Attempt counting** | 1-indexed: 1 = first try, `max_retries+1` = final try |
| **Exception handling** | Catches all `Exception` (not `BaseException` — lets KeyboardInterrupt through) |
| **Delay placement** | Only between attempts, not after the last one |
| **Exception propagation** | Re-raises the **last** exception (most recent failure state) |
| **Context mutation** | Passed by reference — task functions mutate it in-place |

#### Test Cases Covered

1. **Success on first try**: `attempts == 1`, function called once
2. **Success after failures**: Flaky function fails twice, succeeds on 3rd → `attempts == 3`
3. **Total failure**: Always raises → propagates exception after `max_retries+1` attempts

### Function 3: `run_dag(tasks, context)` — Full DAG Execution

**Purpose**: Orchestrate the complete DAG run with dependency ordering, shared context, and failure handling.

#### Specification

- Compute topological order using `topological_order(tasks)`
- Execute each task in that order via `run_task_with_retry`
- Pass **same `context` dict** to every task (shared mutable state)
- Record results per task:
  - Success: `{"status": "success", "attempts": N}`
  - Failure: `{"status": "failed", "attempts": N, "error": str(exc)}`
- **Stop on first failure** — don't run downstream tasks (Airflow behavior)
- Return `{"order": [...], "task_results": {...}}`

#### Implementation Logic

```python
def run_dag(tasks: Dict[str, Task], context: dict) -> dict:
    """
    Run every task in `tasks` in an order that respects dependencies
    (use topological_order), passing the SAME `context` dict to every task
    (so a downstream task can read what an upstream task wrote into it —
    e.g. context["extract"] = [...] written by the "extract" task, read by
    the "score" task).

    For each task, run it via run_task_with_retry and record:
      task_results[name] = {"status": "success", "attempts": N}
    on success, or, if it ultimately fails:
      task_results[name] = {"status": "failed", "attempts": N, "error": str(exc)}
    and then STOP — don't run any tasks that come after a failed task in
    the order (this mirrors Airflow: downstream tasks don't run if an
    upstream one fails).

    Return {"order": <the order you computed>, "task_results": task_results}.
    """
    order = topological_order(tasks)
    task_results = {}

    for name in order:
        task = tasks[name]
        try:
            attempts = run_task_with_retry(task, context)
            task_results[name] = {"status": "success", "attempts": attempts}
        except Exception as e:
            # Task failed after all retries
            attempts = task.max_retries + 1
            task_results[name] = {
                "status": "failed",
                "attempts": attempts,
                "error": str(e)
            }
            # Stop — don't run downstream tasks (Airflow behavior)
            break

    return {"order": order, "task_results": task_results}
```

#### Key Design Decisions

| Aspect | Implementation |
|--------|----------------|
| **Context sharing** | Single `context` dict passed by reference — upstream writes visible to downstream |
| **Failure handling** | `break` on first failure — matches Airflow's "fail fast" for upstream tasks |
| **Attempt count on failure** | Always `max_retries + 1` (all attempts exhausted) |
| **Result structure** | Mirrors Airflow task instance state: status + attempts + optional error |
| **No partial results for downstream** | Failed task's downstream tasks simply absent from `task_results` |

## Code Logic Deep Dive: How the Pieces Fit Together

### The Task Dataclass

```python
@dataclass
class Task:
    name: str
    fn: Callable[[dict], None]        # Called as fn(context) → mutates context in place
    depends_on: List[str] = field(default_factory=list)
    max_retries: int = 0
    retry_delay_seconds: float = 0.0
```

- **`fn` signature**: Takes `context` dict, returns `None`, mutates `context` in-place
- **`depends_on`**: List of task names that must complete before this task
- **`max_retries`**: Additional attempts beyond the first (Airflow semantics)
- **`retry_delay_seconds`**: Delay between retries (simulated with `time.sleep`)

### Data Flow Through the DAG

```
┌─────────────────────────────────────────────────────────────────┐
│                        SHARED CONTEXT                           │
│  {}  →  extract  →  {"image_paths": [...]}                      │
│                    →  score      →  + {"per_image_counts": {...},│
│                    →  load       →  + {"total_detections": N,    │
│                    →  notify     →  + {"report_written": True,   │
│                                       "notified": True}          │
└─────────────────────────────────────────────────────────────────┘
```

Each task reads what upstream tasks wrote — this is the **XCom-like** pattern (Airflow's cross-task communication).

### notify retry count
**3 attempts** — first 2 failed with simulated transient failures, 3rd succeeded (see `dag_run_summary.json`)

### Branch Independence
The `load` task succeeds independently of `notify` because they are **sibling tasks** in the DAG — both depend on `score` but neither depends on the other. In a properly designed DAG, failures in one branch should not affect unrelated parallel branches. The orchestrator runs tasks in topological order and only stops executing **downstream** tasks of a failed task. Since `load` and `notify` are independent branches after `score`, `load` completes successfully even though `notify` initially fails and retries. This demonstrates that DAGs model true parallelism where branch isolation is preserved — a failure in one notification webhook shouldn't prevent writing the batch report.

### Retry Cost Under FinOps
If `notify` were a metered API call (e.g., paid per webhook delivery attempt), the current blind retry strategy (fixed 3 retries for any failure) would be costly. Changes to consider:

1. **Exponential backoff** instead of fixed delay — reduces load on the target service and avoids hammering a failing endpoint
2. **Retry budgets** — cap total retry attempts across the pipeline, not per-task
3. **Failure classification** — only retry on transient errors (5xx, timeout), not permanent ones (4xx, auth failure)
4. **Idempotency keys** — ensure retries don't cause duplicate side effects
5. **Cost-aware retry policies** — cheaper tasks can retry more aggressively; expensive metered calls should have stricter limits

"Retry every failed task the same way" is risky because it ignores the cost profile and failure semantics of different tasks. A $0.01/database write retry is very different from a $0.50/SMS webhook retry. Uniform retry policies can lead to runaway costs during cascading failures.

## Appendix: Complete `src/mini_orchestrator.py` (Final Version)

```python
"""
A tiny local DAG orchestrator — enough to demonstrate the two ideas from
this week's lecture without needing an actual Airflow install (a scheduler,
webserver, and metadata database is a lot of infra for a 110-minute
session):

  1. A DAG is a dependency graph of tasks, executed in an order that
     respects those dependencies (topological order) — not just top to
     bottom in the file.
  2. Individual task retry: a task that fails transiently should be retried
     some number of times before the whole DAG is considered failed, the
     same as Airflow's per-task `retries` parameter.

Fill in the three functions marked # TODO. The `Task` dataclass above them
is given.
"""
import time
from dataclasses import dataclass, field
from typing import Callable, Dict, List


@dataclass
class Task:
    name: str
    fn: Callable[[dict], None]  # called as fn(context) -> mutates context in place
    depends_on: List[str] = field(default_factory=list)
    max_retries: int = 0
    retry_delay_seconds: float = 0.0


# ---------------------------------------------------------------------------
# Part 1 — Topological order (a DAG is a dependency graph, not a list)
# ---------------------------------------------------------------------------

def topological_order(tasks: Dict[str, Task]) -> List[str]:
    """Given a dict of {task_name: Task}, return a list of task names such
    that every task appears AFTER all the tasks in its `depends_on`.

    If there's more than one valid order (e.g. two independent tasks that
    both depend on the same upstream task), any valid order is fine.

    If the tasks contain a dependency cycle (or a task depends on a name
    that doesn't exist in `tasks`), raise ValueError.

    Hint: Kahn's algorithm — compute in-degree (number of dependencies) for
    every task, repeatedly pick a task with in-degree 0, "remove" it
    (decrementing the in-degree of everything that depended on it), and
    append it to the result. If you run out of in-degree-0 tasks before
    placing every task, there's a cycle.
    """
    # Build adjacency list and compute in-degrees
    in_degree = {name: 0 for name in tasks}
    adj = {name: [] for name in tasks}

    # Check for missing dependencies and build graph
    for name, task in tasks.items():
        for dep in task.depends_on:
            if dep not in tasks:
                raise ValueError(
                    f"Task '{name}' depends on missing task '{dep}'"
                )
            adj[dep].append(name)
            in_degree[name] += 1

    # Kahn's algorithm: start with nodes that have in-degree 0
    queue = [name for name, deg in in_degree.items() if deg == 0]
    result = []

    while queue:
        # Pop a task with in-degree 0 (any valid order is fine)
        current = queue.pop(0)
        result.append(current)

        # Decrement in-degree of all tasks that depend on current
        for neighbor in adj[current]:
            in_degree[neighbor] -= 1
            if in_degree[neighbor] == 0:
                queue.append(neighbor)

    # If we couldn't place all tasks, there's a cycle
    if len(result) != len(tasks):
        raise ValueError("Dependency cycle detected in tasks")

    return result


# ---------------------------------------------------------------------------
# Part 2 — Retry a single task
# ---------------------------------------------------------------------------

def run_task_with_retry(task: Task, context: dict) -> int:
    """Run `task.fn(context)`. If it raises, retry up to `task.max_retries`
    additional times (so max_retries=2 means up to 3 total attempts),
    sleeping `task.retry_delay_seconds` between attempts (use time.sleep).

    If the task eventually succeeds, return the number of attempts it took
    (1 if it succeeded on the first try).

    If it never succeeds, let the LAST exception propagate (don't swallow
    it) after all retries are exhausted.
    """
    last_exception = None
    max_attempts = task.max_retries + 1

    for attempt in range(1, max_attempts + 1):
        try:
            task.fn(context)
            return attempt
        except Exception as e:
            last_exception = e
            if attempt < max_attempts:
                time.sleep(task.retry_delay_seconds)

    # All retries exhausted, propagate the last exception
    raise last_exception


# ---------------------------------------------------------------------------
# Part 3 — Run the whole DAG
# ---------------------------------------------------------------------------

def run_dag(tasks: Dict[str, Task], context: dict) -> dict:
    """Run every task in `tasks` in an order that respects dependencies
    (use topological_order), passing the SAME `context` dict to every task
    (so a downstream task can read what an upstream task wrote into it —
    e.g. context["extract"] = [...] written by the "extract" task, read by
    the "score" task).

    For each task, run it via run_task_with_retry and record:
      task_results[name] = {"status": "success", "attempts": N}
    on success, or, if it ultimately fails:
      task_results[name] = {"status": "failed", "attempts": N, "error": str(exc)}
    and then STOP — don't run any tasks that come after a failed task in
    the order (this mirrors Airflow: downstream tasks don't run if an
    upstream one fails).

    Return {"order": <the order you computed>, "task_results": task_results}.
    """
    order = topological_order(tasks)
    task_results = {}

    for name in order:
        task = tasks[name]
        try:
            attempts = run_task_with_retry(task, context)
            task_results[name] = {"status": "success", "attempts": attempts}
        except Exception as e:
            # We need to know how many attempts were made before failure
            # run_task_with_retry propagates the exception after all retries
            # The number of attempts = max_retries + 1
            attempts = task.max_retries + 1
            task_results[name] = {
                "status": "failed",
                "attempts": attempts,
                "error": str(e),
            }
            # Stop running further tasks (Airflow behavior)
            break

    return {"order": order, "task_results": task_results}
```
