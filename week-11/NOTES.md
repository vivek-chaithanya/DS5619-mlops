## pruned_dense_fp32 vs. pruned_sparse_coo

In `compression_report.json`, both `pruned_dense_fp32` and `pruned_sparse_coo` evaluate the exact same model weights:
- **Accuracy:** `99.67%` (identical)
- **Inference Latency:** `~2.94 ms` per evaluation pass (identical)
- **Size in Storage:** `1024 bytes` (dense) vs. `616 bytes` (sparse COO) — a **1.66× compression ratio** achieved solely by altering the storage representation.

### Why do they share identical accuracy?
Because the mathematical values in both representations are identical. In `prune_weights(weights, sparsity=0.70)`, 179 of the 256 weights (those with the smallest absolute values) are zeroed out to `0.0`. The surviving 77 weights retain their exact floating-point values and spatial positions. Whether those weights are held in a contiguous 256-element dense array or serialized as non-zero `(index, value)` coordinate pairs, the underlying linear classifier calculates the exact same dot product:
$$\hat{y} = \mathbb{I}\left(\sum_{i=0}^{255} w_i x_i > 0\right) = \mathbb{I}\left(\sum_{i \in \text{nonzero}} w_i x_i > 0\right)$$
Hence, predictions on all 300 test examples are byte-for-byte identical.

### Why is there a massive gap in `size_bytes`? (The Pruning Pitfall)
This disparity directly illustrates the **"pruning pitfall"** emphasized in the lecture: **pruning floating-point values to zero does not save a single byte of memory if the tensor is stored in standard dense format.**

1. **The Dense Pitfall (`pruned_dense_fp32` = 1024 bytes):**
   Standard numerical libraries and runtime runtimes allocate flat contiguous memory blocks:
   $$\text{Size}_{\text{dense}} = N \times B = 256 \times 4\text{ bytes} = 1024\text{ bytes}$$
   A floating-point `0.0` in IEEE 754 single precision occupies exactly 32 bits (4 bytes: `0x00000000`), the exact same memory footprint as `3.14159` or `-1.875`. Therefore, zeroing out 70% of the weights on paper leaves storage completely unchanged at 1024 bytes ($1.00\times$ compression).

2. **The Sparse COO Trade-off (`pruned_sparse_coo` = 616 bytes):**
   To materialize actual storage savings from pruning, weights must be transitioned to a sparse representation, such as Coordinate Format (COO). In COO format, explicitly zero entries are dropped entirely, but **every surviving non-zero parameter must pay an indexing tax** to record its original spatial position:
   $$\text{Size}_{\text{COO}} = N_{\text{nonzero}} \times (\text{value\_bytes} + \text{index\_bytes})$$
   Here, each non-zero float costs 4 bytes for the value plus 4 bytes for a 32-bit integer index (total 8 bytes per survivor).
   With 77 non-zero weights surviving:
   $$\text{Size}_{\text{COO}} = 77 \times (4 + 4) = 77 \times 8 = 616\text{ bytes} \quad (1.66\times \text{ compression})$$

3. **The 50% Breakeven Threshold:**
   Because each survivor in COO requires 8 bytes instead of the dense 4 bytes, sparse storage only yields net savings when:
   $$N_{\text{nonzero}} \times 8 < N \times 4 \implies \frac{N_{\text{nonzero}}}{N} < \frac{4}{8} = 0.50$$
   That is, **sparsity must strictly exceed 50%** before COO saves any memory over dense FP32. If a model is pruned to only 30% sparsity ($N_{\text{nonzero}} = 179$), COO storage would require $179 \times 8 = 1432\text{ bytes}$, which is **39.8% larger** than the original unpruned dense model!


## The 0.95-sparsity experiment

When `PRUNE_SPARSITY` is increased from `0.70` to `0.95` in `src/run_pipeline.py`, model accuracy experiences a catastrophic collapse:

| Sparsity Level | Pruned Weights | Surviving Weights ($N_{\text{nonzero}}$) | Informative Surviving (out of 40) | COO Size | Model Accuracy |
|:---:|:---:|:---:|:---:|:---:|:---:|
| **0.00 (Baseline)** | 0 | 256 | 40 | 2048 B | **100.00%** |
| **0.70 (Default)** | 179 | 77 | 40 | 616 B | **99.67%** |
| **0.80** | 204 | 52 | 40 | 416 B | **99.67%** |
| **0.85** | 217 | 39 | 39 | 312 B | **98.00%** |
| **0.90** | 230 | 26 | 26 | 208 B | **87.00%** |
| **0.95 (Cliff)** | 243 | 13 | 13 | 104 B | **79.33%** |

### Why does this collapse make sense given the 40 informative weights?
The weight vector generated by `generate_for_student.py` contains 256 total parameters constructed with a deliberate bimodal magnitude distribution:
- **40 Informative Weights:** Drawn from $[-2.0, 2.0]$ with an enforced minimum magnitude threshold $|w_i| \ge 0.50$.
- **216 Noise Weights:** Drawn uniformly from $[-0.03, 0.03]$, ensuring $|w_i| \le 0.03$.
- **Structural Gap:** There is a guaranteed $\approx 17\times$ magnitude gap ($0.50 / 0.03 \approx 16.67$) between the smallest informative weight and the largest noise weight.

Because magnitude-based pruning unconditionally zeroes out weights with the smallest absolute values:
1. **At 70% Sparsity ($n_{\text{prune}} = \lfloor 0.70 \times 256 \rfloor = 179$):**
   The 179 smallest weights are drawn entirely from the pool of 216 noise weights ($179 < 216$). All 40 informative weights remain completely untouched. The surviving weight set contains all 40 signal weights plus $216 - 179 = 37$ residual noise weights. The decision hyperplane is practically unperturbed, preserving **99.67% accuracy**.
2. **At 95% Sparsity ($n_{\text{prune}} = \lfloor 0.95 \times 256 \rfloor = 243$):**
   The algorithm exhausts all 216 noise weights and is forced to prune:
   $$243 - 216 = 27 \text{ informative weights}$$
   Only $40 - 27 = 13$ informative weights survive out of the original 40. Over **67.5% of the model's true predictive features are zeroed out**.
   With only 13 remaining features, the model's capacity to represent the true label-generating dot product is crippled, and accuracy plummets from 99.67% down to **79.33%** (and collapses to ~50% random guessing at $\ge 98\%$ sparsity).

This demonstrates the fundamental limit of unstructured pruning: compression is safe only within the model's over-parameterization margin. Once pruning cuts into the core subspace of informative features, performance degrades precipitously.
